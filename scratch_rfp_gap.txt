0.2 Conventions used throughout this document
Database objects: snake_case table/column names, sp_ prefix for stored procedures (sp_FIM_ for this pass, matching sp_CreatePurchaseOrder / sp_RecalculateInventoryBalance precedent).
API authorization: [Authorize(Policy = "<module>.read"/"<module>.write")] on every mutating/sensitive endpoint — the AGENTS.md “missing [Authorize] = anonymous access” lesson applies to every new endpoint below.
New permission modules (where introduced) follow the existing operational-vs-administrative segregation documented in docs/PERMISSIONS.md and docs/MODULE_SEGREGATION_REVIEW.md.
Dual database provider: every new table/procedure targets SQL Server T-SQL (production) with the existing SQLite EnsureCreated() dev fallback in mind — avoid SQL Server-only syntax in paths the EF Core model also needs to satisfy.
IMAL (core banking rate feed) and GL (general ledger reconciliation) already exist as concepts in PMIMS (README.md, ExternalServices.cs); GFS, Phoenix and SAP do not appear anywhere in the current codebase — those integrations are greenfield and scoped conservatively (adapter interfaces, not vendor-specific SDKs baked into the core).

2. Mobile App Module (Android with NFC)
New Android client + a thin mobile-facing REST surface reusing existing inventory/transfer/intake services.
Architecture / Design
Component flow: Android app (Kotlin, MVVM) → OAuth2 login → PMIMS.WebAPI mobile endpoints → existing IInventoryRepository / branch-transfer / intake services (no duplicate business logic). Local Room (SQLite) cache mirrors server state for offline lookup; WorkManager drives sync-on-connect.
NFC/scan flow: CameraX + ML Kit Barcode Scanning (QR/1D barcodes) and Android NfcAdapter (NDEF reads for NFC-tagged bins/packages) resolve a scanned code to inventory_items.serial_number (already unique-indexed) before calling the relevant confirm/verify endpoint.
Auth: extend the existing JWT login with a mobile-appropriate OAuth2 flow (longer-lived refresh token, device-bound) rather than replacing PMIMSControllers.GenerateJwt — same claims shape (roles + perm:* claims), so server-side authorization is unchanged.
Database Changes
device_registrations (device_id PK, user_id FK app_users, platform, app_version, push_token, last_sync_at, is_active).
mobile_sync_cursors (user_id, entity_type, last_synced_at) — per-user incremental sync watermark, same pattern as fim_sync_logs' delta model.
No changes to inventory_items / branch_transfers / pending_intakes — the mobile module is a client, not a new source of truth.
API Changes
POST /api/auth/mobile/token — OAuth2 password/refresh grant, longer refresh-token TTL, device_id bound.
GET /api/mobile/inventory/lookup?serial= — resolves a scanned serial to item/location/status.
POST /api/mobile/transfers/{transferId}/confirm, POST /api/mobile/intake/{poId}/verify — thin wrappers over existing repository methods (ReceiveBranchTransferAsync / IntakeInventoryItemsAsync).
GET /api/mobile/notifications — pending actions relevant to the device's user (reuses GetPendingWorkflowInstancesForUserAsync).
GET /api/mobile/sync/delta?since= — mirrors the FIM delta-sync pattern for offline cache refresh.
New module key mobile (operational tier): mobile.read / mobile.write policies, same [Authorize(Policy=...)] convention as every other module.
Code Implementation
PMIMSControllers.Mobile.cs — new partial class, thin delegation only, no new business rules.
Android: Kotlin, minSdk 21 (Android 5.0 Lollipop) for backward compatibility with AppCompat/Room; Retrofit + OkHttp for REST; Room for the offline cache; WorkManager for background sync; CameraX/ML Kit for scanning.
Screens (Fragment + ViewModel each): Inventory Lookup, Transfer Confirmation, Receipt Verification, Barcode/QR Scan, Notifications.
Configuration
Mobile:RefreshTokenExpiryDays, Mobile:MinSupportedAppVersion (server-enforced minimum, rejects stale clients).
Android build variants carry the API base URL per environment (Dev/UAT/Stage/Prod).
Testing Strategy
Android: JUnit + Espresso (UI flows), Robolectric for ViewModel logic.
Backend: xUnit for PMIMSControllers.Mobile.cs against mocked IInventoryRepository.
UAT: warehouse operator scans an NFC-tagged sealed package at the receiving dock while offline; app queues the intake verification locally; on reconnect, sync-on-connect pushes it and PMIMS reflects RECEIVED status within one sync cycle.
Documentation
Mobile app end-user guide (per screen), API reference addendum for /api/mobile/*, offline-conflict-resolution note (last-write-wins with server-side revalidation against RowVersion where applicable).
3. KFH Integration Middleware (Web Services Based)
SOAP/WCF adapter layer routing outbound integrations (IMAL, GL, and the RFP-named GFS/Phoenix once scoped) through KFH's middleware instead of calling core systems directly.
Architecture / Design
PMIMS.Infrastructure → IIntegrationMiddlewareClient (new Application-layer interface) → KfhMiddlewareSoapClient (WCF BasicHttpBinding, mTLS client certificate) → KFH Integration Middleware → IMAL / GL / GFS / Phoenix.
Existing direct call sites (RateFeedService's IMAL fallback, ReconciliationService's GL mapping) are redirected through this client instead of calling the target system directly — the middleware becomes the single egress point, matching the RFP's “route all integration touch points through KFH Integration Middleware” requirement.
A local outbound queue + dead-letter table absorbs middleware unavailability so PMIMS operations (e.g., a reconciliation run) don't hard-fail on a transient integration outage.
Database Changes
integration_outbound_messages (message_id, target_system, message_type, payload_xml, status_code [PENDING/SENT/FAILED/DEAD_LETTER], attempt_count, last_attempt_at, created_at).
integration_dead_letters (dead_letter_id, message_id FK, failure_reason, moved_at).
Index on (status_code, target_system) for the retry sweeper's polling query.
API Changes
No new public integration endpoints — the change is internal (service call sites redirected).
GET /api/integration/outbound-messages, POST /api/integration/outbound-messages/{id}/retry — ops visibility/manual-replay, new integration_ops module (admin tier).
Code Implementation
IIntegrationMiddlewareClient.SendAsync(targetSystem, messageType, payloadXml) (PMIMS.Application).
KfhMiddlewareSoapClient (PMIMS.Infrastructure) — WCF ChannelFactory<IKfhMiddlewarePortType> against the middleware's WSDL; Polly-driven exponential-backoff retry; on exhaustion, writes to integration_dead_letters instead of throwing to the caller.
RateFeedService and ReconciliationService updated to depend on IIntegrationMiddlewareClient instead of the current direct HTTP/simulated call — behind a feature flag so dev/UAT can keep the existing simulated feed.
Configuration
IntegrationMiddleware:Endpoint, :ClientCertificateThumbprint, :RetryMaxAttempts, :RetryBackoffSeconds, :Enabled (falls back to today's simulated feed when false).
Testing Strategy
Unit tests mocking IIntegrationMiddlewareClient for both RateFeedService and ReconciliationService call sites.
Integration test against a WireMock/soapUI-hosted SOAP stub simulating the middleware's WSDL contract.
UAT: simulate a middleware outage, confirm the message lands in the dead-letter table and is successfully replayable via the retry endpoint.
Documentation
Middleware message catalog (message_type → target_system → XSD schema), retry/dead-letter-queue operational runbook.
4. SAP Enterprise Business Intelligence (EBI) Integration
Scheduled ETL export from PMIMS reporting views into a SAP BusinessObjects/BW-compatible landing format — batch, not live SAP calls.
Architecture / Design
PMIMS SQL Server (star-schema reporting views) → scheduled export job (hosted BackgroundService, same pattern as ReservationCleanupService) → flat-file drop (pipe-delimited, BODS-import-ready) → SAP Business Objects Data Services (BODS) / BW load.
OLAP cube exports are produced from the same fact views in a SAP-compatible dimensional shape (date, metal type, branch, ownership type as dimensions; quantity and KWD value as measures).
Database Changes
Views: vw_sap_inventory_fact, vw_sap_transaction_fact, vw_sap_valuation_fact — star-schema shaped over inventory_balances, inventory_transactions, valuation_snapshots.
sap_export_runs (run_id, export_type, row_count, started_at, completed_at, status_code, file_path) — run history/audit.
API Changes
POST /api/sap/exports/{exportType}/run — manual trigger (sap_integration module, .write).
GET /api/sap/exports — run history.
Code Implementation
ISapExportService / SapExportService generating the documented pipe-delimited extract per exportType, hosted as a BackgroundService on a configurable cron (default nightly 02:00 Kuwait time).
Configuration
SapIntegration:ExportScheduleCron, :ExportDropFolder, :Enabled.
Testing Strategy
Unit tests validating extract row counts and column mapping against seeded data.
UAT: run an export, load the sample file into a SAP BODS staging table (or an equivalent mock loader) and confirm zero truncation/type-mismatch errors.
Documentation
ETL pipeline document (source view → transform → target field mapping), OLAP cube dimension/measure reference.
5. Dynamic Business Validation Rules Engine [DELIVERED — see §0.1b]
In-database rule catalog + in-memory evaluation engine, invoked as a pre-check inside existing transfer/receipt/reservation/PO flows — additive to, not a replacement for, current hard-coded guards (e.g., the vendor Sharia-compliance check in sp_CreatePurchaseOrder).
Architecture / Design
Mirrors the existing Maker-Checker workflow engine's “pluggable step” philosophy, but for validation rather than approval routing.
Extension points: transfer initiation, receipt/intake validation, customer eligibility, rate thresholds, inventory availability checks — called from the corresponding IInventoryRepository methods before the existing stored-procedure-level checks run.
Rules are stored as a structured predicate tree (field/operator/value/and-or), not executable code — this closes off a code-injection surface entirely, at the cost of expressiveness (acceptable given the RFP's stated rule categories are all simple comparisons/thresholds).
Database Changes
business_rules (rule_id, rule_code, rule_name, rule_type [TRANSFER_LIMIT/RECEIPT_VALIDATION/CUSTOMER_ELIGIBILITY/RATE_THRESHOLD/INVENTORY_CHECK], expression_json, severity [BLOCK/WARN], version, is_active, effective_from, effective_to, created_by, created_at).
business_rule_evaluations (evaluation_id, rule_id, entity_type, entity_id, result [PASS/FAIL/WARN], evaluated_at, context_json) — evaluation audit trail.
API Changes
GET/POST/PUT /api/rules, POST /api/rules/{id}/activate, POST /api/rules/{id}/deactivate, GET /api/rules/{id}/versions, POST /api/rules/evaluate (ad-hoc test-evaluate).
New rules_engine module, admin tier (.read/.write), same segregation pattern as workflow_design vs. workflows.
Code Implementation
IRuleEngineService.EvaluateAsync(ruleType, context) (PMIMS.Application) — walks active rules of that type by version, evaluates the predicate tree in-memory, returns pass/fail/warnings.
Called from InitiateBranchTransferAsync, IntakeInventoryItemsAsync, ReserveStockAsync, and PO creation as an additive pre-check.
Optional sp_EvaluateBusinessRule T-SQL mirror for direct-DB batch validation scenarios.
In-memory rule cache with save-triggered invalidation (RulesEngine:CacheTtlSeconds).
Configuration
RulesEngine:CacheTtlSeconds, per-rule_type feature flags (RulesEngine:Enabled:<RuleType>).
Testing Strategy
Unit tests per predicate operator (>=, <=, in, between) and per rule_type.
Regression test confirming existing hard-coded validations (e.g., Sharia vendor check) still fire even when the rules engine is disabled.
UAT: a business user adds “no single transfer over 5kg gold without dual approval” with zero code deploy; confirm it blocks a 6kg transfer attempt and the admin UI shows the rule as active with correct version history.
Documentation
Rule-authoring guide, predicate-tree JSON schema reference, admin UI screen (screen-rules) walkthrough.
6. Enhanced Audit Trail UI [DELIVERED — see §0.1b]
Built directly on the existing audit_logs table and GET /api/reports/audit-logs endpoint — adds search, filtering, export and tamper-detection without changing the write path (every module already writes here).
Architecture / Design
Read-side enhancement only: every module already calls SaveAuditLogAsync on mutating actions, so no new instrumentation is needed at the write path — this item is entirely about making the existing audit_logs data explorable.
Tamper-detection: a row_hash column (SHA-256 over the row's other columns, computed at insert time) lets the UI recompute-and-compare on read; a mismatch surfaces as a tamper indicator per row.
Database Changes
ALTER audit_logs ADD entity_type, entity_id, row_hash (all nullable — backward compatible with existing rows, which show “Unverified (pre-dates hashing)” rather than a false tamper flag).
CREATE FULLTEXT INDEX on audit_logs(action_description) for full-text search across action descriptions.
sp_SearchAuditLogs — dynamic filter (user/timestamp/action type/module/entity/status) built from sanitized parameters, never string-concatenated (ties directly into Item 11's inline-query policy).
API Changes
GET /api/reports/audit-logs/search?query=&user=&module=&entityType=&status=&from=&to=&page= — paginated, filtered, full-text.
GET /api/reports/audit-logs/{id} — single-entry drill-down with recomputed tamper-check status.
GET /api/reports/audit-logs/export?format=pdf|xlsx|csv — under the existing reports.read policy.
Code Implementation
Extend IInventoryRepository.GetAuditLogsAsync with a filtered/paged overload backed by sp_SearchAuditLogs.
New AuditExportService for PDF/Excel/CSV/print-friendly rendering (reused by Item 4's SAP export and Item 7's scheduled reports).
Configuration
Audit:FullTextSearchEnabled, Audit:ExportMaxRows (guard against unbounded exports).
Testing Strategy
Unit tests for hash computation/verification and for the dynamic filter builder, including SQL-injection negative test cases.
UAT: search “purchase order” across 90 days of logs, filter by user + module, export to Excel, confirm the exported row count matches the on-screen filtered count.
Documentation
Audit trail explorer user guide; tamper-detection methodology note (row_hash detects in-place row edits, not deletions — pair with DB-level access controls for deletion protection).

9. Data Dictionary (Excel Format)
A generated, not hand-maintained, Excel workbook — PMIMS already carries full schema metadata (EF Core model + database/schema.sql), so the dictionary should be produced from that source of truth to avoid drift.
Approach
A small offline generator (tools/generate-data-dictionary/) reads INFORMATION_SCHEMA (or the EF Core model) and cross-references a curated business_glossary.json (business entity/attribute names and definitions the schema alone can't infer), emitting one row per column with exactly the RFP-required fields: Table Name, Associated Business Entity Name, Definition of Entity, Column Name, Associated Business Attribute Name, Business Attribute Definition, Data Type/Scale/Precision, Nullability, Format Pattern, Domain Range, Primary Key, Foreign Keys, Alternate Key, Subject Area.
ISO/IEC 11179-4 compliance: each Business Attribute Definition follows the standard's precise / concise / non-circular / unit-of-measure-stated rules; a short authoring checklist ships in the tool's README.
Deliverable
PMIMS_Data_Dictionary.xlsx — one worksheet per Subject Area (Inventory Ledger, Customer Holdings, Transactions, Workflows & Security, FIM Integration, Reconciliation & Valuation, ...) plus an index sheet.
Testing / Acceptance
Generated row count matches INFORMATION_SCHEMA.COLUMNS count for the target database.
DBA sign-off spot-check.
Regenerate-and-diff wired into CI so drift between the dictionary and the live schema is caught automatically (shared mechanism with Item 15's lifecycle tracking).
10. Data Model (CA Erwin 9.x Format)
database/schema.sql is the authoritative DDL; the conversion path is DDL → Erwin reverse-engineer import, not a hand-built model file that risks drifting from the real schema.
Approach
1) Stand up a disposable SQL Server instance from database/schema.sql + database/procedures.sql.
2) Erwin Data Modeler 9.x “Reverse Engineer” (ODBC) against that instance produces the physical model.
3) Hand-author the logical-level overlay in Erwin — business names, relationship cardinality, bi-directional relationship phrases (e.g., “InventoryItem is stored in InventoryLocation” / “InventoryLocation stores InventoryItem”) — since phrasing/cardinality is a modeling decision Erwin can't infer from DDL alone.
4) Export Physical and Logical model views plus a subject-area diagram per module, using the same Subject Area grouping as Item 9's data dictionary so both deliverables stay consistent with each other.
Deliverable
PMIMS_DataModel.erwin (or .ERX interchange format, so the round-trip can be validated without requiring a licensed Erwin seat).
Validation
Round-trip test: export .ERX, re-import into a clean Erwin session, diff entity/attribute/relationship counts against the source to confirm zero data loss before hand-off.
Maintenance note
One-time-per-schema-version artifact — re-run steps 1–4 whenever schema.sql changes materially; tie to the same CI schema-drift check as Item 9.
11. Remove Inline Queries
Audit + enforce. PMIMS already leans on stored procedures for its critical write paths (sp_CreatePurchaseOrder, sp_RecalculateInventoryBalance, etc.) — this item closes the remaining gaps and makes the pattern unbreakable going forward.
Audit findings (this pass)
The pre-existing FIM mock in ExternalServices.cs called ExecuteSqlRawAsync with parameterized placeholders (not string-concatenated, but still raw SQL in application code). It has been removed as part of the Item 1 rebuild — the new FimService uses EF Core LINQ plus the sp_FIM_* procedures exclusively, closing that instance.
Recommended next step: run a repo-wide grep for ExecuteSqlRaw, FromSqlRaw, and any string-built SQL across backend/ and catalog every remaining hit with file:line before remediation.
Remediation plan
For each hit: convert to a parameterized stored procedure call (preferred — consistent with the sp_ convention) or a pure EF Core LINQ query. Never string-concatenated SQL, regardless of parameterization.
Add a Roslyn analyzer rule to the existing PMIMS.Analyzers / PMIMS.Analyzers.Test project scaffold that flags ExecuteSqlRaw / FromSqlRaw / ad-hoc SqlCommand construction built from a non-constant, non-parameterized string — build-breaking severity.
CI/CD
Wire the analyzer as an error-severity rule (Directory.Build.props / .editorconfig) so dotnet build fails on a violation.
Document the rule as a required pre-merge check in the code-review policy.
Documentation
